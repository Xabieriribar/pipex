Your evaluator will try to break `pipex` in four dimensions:

1. Interface: Build rules, arguments, and allowed functions.
2. Behavior: Does it behave exactly like `< file1 cmd1 | cmd2 > file2`. 
3. Robustness: Crashes, leaks, fd handling, permissions, PATH, weird commands.
4. Understanding: Can you explain and adapt code on the spot. 

Below is a full evaluation plan you can rehearse yourself on a clean Linux VM.

---

## 0. Ground rules you will be graded against

You must pass these at all times or you get 0:

* The repo must contain: `Makefile, *.c, *.h`. `./pipex` must compile with `cc` and flags `-Wall -Wextra -Werror`. The Makefile must have rules `all`, `clean`, `fclean`, `re`, and `$(NAME)` and must not relink if nothing changed. 
* `./pipex file1 cmd1 cmd2 file2` must behave exactly like shell:
  `< file1 cmd1 | cmd2 > file2`. 
* Only allowed syscalls/functions: `open`, `close`, `read`, `write`, `malloc`, `free`, `perror`, `strerror`, `access`, `dup`, `dup2`, `execve`, `exit`, `fork`, `pipe`, `unlink`, `wait`, `waitpid`, plus your own `ft_printf` equivalent. Libft is allowed. No other helpers from libc unless they are part of libft you copied. 
* No segfault, no bus error, no double free, no unexpected exit. If it crashes you get 0. 
* No memory leaks at exit. Leaks are not tolerated. 
* Mandatory must be perfect or bonus is ignored. 

Interpretation: if any of the mandatory checks below fails, you are dead even if your multipipe / here_doc works.

So you prepare for these checks.

## 2. Functional behavior tests

Goal: confirm identical effect to `< infile cmd1 | cmd2 > outfile`.

For each test below do:

1. Run your program.
2. Run the equivalent shell pipeline.
3. `diff` outputs and compare exit behavior.

Assume:

```bash
echo -e "hello\nworld\nhola\n42\n" > infile
echo -e "abc def ghi\nsomething something 42\n" > otherfile
> emptyfile  # create empty file
rm -f outfile out_shell out_pipex
```

### 2.1 Simple two-command pipeline

Command under test:

```bash
./pipex infile "cat" "wc -l" outfile
< infile cat | wc -l > out_shell
```

Check:

* `diff outfile out_shell` must be empty.
* Example expected content: number of lines in `infile`.

This proves: read from file1, pipe to cmd1, pipe to cmd2, write to file2 exactly. 

### 2.2 With flags and args that include spaces

```bash
./pipex infile "grep o" "wc -w" outfile
< infile grep o | wc -w > out_shell
diff outfile out_shell
```

This confirms you split commands correctly and pass arguments (not just command name). The subject says `cmd1` and `cmd2` are "shell commands with their parameters". 
If your parser fails quotes or spaces you lose points.

Edge: `"grep o"` must exec binary `grep` with arg `o`, not try to exec `"grep o"` literally.

### 2.3 Command with absolute path

```bash
./pipex infile "/bin/grep 4" "/usr/bin/wc -l" outfile
< infile /bin/grep 4 | /usr/bin/wc -l > out_shell
diff outfile out_shell
```

Confirms you handle absolute paths. You must not depend only on PATH resolution if a slash is present.

### 2.4 Command with PATH lookup

```bash
./pipex infile "ls -l" "wc -l" outfile
< infile ls -l | wc -l > out_shell
diff outfile out_shell
```

If `ls` is resolved via `PATH`, `execve` must succeed. If you built your own `which` logic, be ready to explain how you parse `PATH`, split by `:`, and check `access(path, X_OK)`.

### 2.5 Outfile creation and truncate

```bash
echo "XXX" > preexisting
./pipex infile "cat" "cat" preexisting
< infile cat | cat > out_shell
diff preexisting out_shell
```

Check that `preexisting` content is replaced, not appended. Shell `>` truncates. Your open on file2 must match `>` semantics: `O_CREAT | O_WRONLY | O_TRUNC` with `0644`.

### 2.6 Outfile create if not exists

```bash
rm -f newfile
./pipex infile "cat" "cat" newfile
< infile cat | cat > out_shell
diff newfile out_shell
ls -l newfile
```

Check file permissions roughly match shell default umask behavior. Minor mode differences are usually accepted but you should open with write and create.

### 2.7 Empty infile

```bash
: > emptyfile           # empty
./pipex emptyfile "cat" "wc -l" outfile
< emptyfile cat | wc -l > out_shell
diff outfile out_shell
```

Expected in both cases: `0` (or `0\n`). Ensures you don't mis-handle EOF and don't hang.

### 2.8 Large input

Stress test with a large file to prove you read/write in chunks and do not store whole file in RAM.

```bash
yes "DATA LINE" | head -n 200000 > bigfile    # ~2e5 lines
./pipex bigfile "grep DATA" "wc -l" outfile
< bigfile grep DATA | wc -l > out_shell
diff outfile out_shell
```

Check runtime and memory. Evaluator might watch `top` or `valgrind --tool=massif`. Your code should stream through pipe. If you read whole file into malloc without limit they will notice.

## 3. Error handling and edge cases

You must reproduce shell-like behavior and good error messages, without crashing. The subject says "If you are unsure, handle errors the same way as the shell command `< file1 cmd1 | cmd2 > file2`". 

You will be judged mainly on:

* return code (exit status),
* use of `perror` / `strerror(errno)` or similar,
* graceful cleanup (close fds, free heap),
* not writing garbage to outfile when something fails before second cmd runs.

### 3.1 Missing infile

```bash
rm -f nofile
./pipex nofile "cat" "wc -l" outfile 2> err_pipex
< nofile cat | wc -l > out_shell 2> err_shell
echo $?
```

Checks:

* Program must not segfault.
* It should print an error close to shell error. Often: `No such file or directory`.
* Outfile should still be created/truncated because shell still runs `> outfile` even if first redirect fails? Careful. Real bash:
  ` < nofile cat | wc -l > outfile`

  * `outfile` exists and gets output "0" from `wc -l` because `cat` got no stdin.
    Your implementation should mimic that behavior as close as possible. You will be asked to justify differences.

High leverage: You must still exec `cmd2` even if `file1` open fails. The second command must not be skipped unless the pipeline would also skip it in shell. Show that you know this.

### 3.2 Infile exists but no read permission

```bash
echo "secret" > protected
chmod 000 protected
./pipex protected "cat" "wc -l" outfile 2> err_pipex
< protected cat | wc -l > out_shell 2> err_shell
ls -l protected
diff outfile out_shell
```

Check:

* You must attempt open("protected", O_RDONLY) and handle `EACCES` with clear error.
* Again, `wc -l` may still run and write something to outfile depending on how you built the pipeline.

If your program just aborts and exits without producing outfile or without running second command, you risk questions.

### 3.3 Command not found: first command invalid

```bash
./pipex infile "nosuchcmd arg1" "wc -l" outfile 2> err_pipex
< infile nosuchcmd arg1 | wc -l > out_shell 2> err_shell
echo $?
diff outfile out_shell
cat err_pipex
cat err_shell
```

Expected:

* You do not crash.
* You likely print something similar to "nosuchcmd: command not found".
* Second command still runs in shell pipeline but gets empty stdin if first child failed to exec. Your code should try to replicate that.

The evaluator will compare `outfile` with `out_shell`. They expect either same data or a strong justification.

You must handle `execve` failure: usually if `execve` returns `-1`, you should `perror("nosuchcmd")` then exit child with `127`. Parent must continue.

### 3.4 Command not found: second command invalid

```bash
./pipex infile "cat" "idontexist please" outfile 2> err_pipex
< infile cat | idontexist please > out_shell 2> err_shell
echo $?
ls -l outfile out_shell
```

Check:

* Outfile should likely be created (or truncated) but probably empty in both cases.
* You should not leave outfile partially open forever.
* You should still close all fds and waitpid both children.

### 3.5 Both commands invalid

```bash
./pipex infile "nope" "stillnope" outfile 2> err_pipex
< infile nope | stillnope > out_shell 2> err_shell
echo $?
```

Again: stability, error messages, cleanup.

### 3.6 No execute permission on binary

```bash
echo -e '#!/bin/sh\necho hi' > script.sh
chmod 000 script.sh
./pipex infile "./script.sh" "wc -l" outfile 2> err_pipex
< infile ./script.sh | wc -l > out_shell 2> err_shell
diff outfile out_shell
cat err_pipex
```

`execve` should fail with `EACCES`. You must report that error cleanly.

### 3.7 Quoting and multiple arguments

```bash
./pipex infile "grep 4 2" "wc -l" outfile
< infile grep 4 2 | wc -l > out_shell
diff outfile out_shell
```

Shell here treats `grep 4 2` as `grep` with two patterns/args `4` and `2`. Your splitter must do the same.
If your split logic only keeps first arg or merges all into one token you will diverge.

If you attempt to implement complex quotes like `"grep 'hello world'"` you must confirm consistent behavior. Evaluator may try:

```bash
./pipex infile "grep \"hello world\"" "wc -l" outfile
< infile grep "hello world" | wc -l > out_shell
diff outfile out_shell
```

If you do not support quotes, be ready to justify. Many evaluators accept basic split by spaces only, but some will test quotes. Prepare.

### 3.8 Handling of `NULL` args / empty command

```bash
./pipex infile "" "wc -l" outfile
```

This is undefined in subject. If you segfault you fail. So defend it. You can:

* detect empty string for cmd1 or cmd2
* print error and exit child
* still not crash parent.

### 3.9 Too few / too many arguments

The subject defines exact interface: `./pipex file1 cmd1 cmd2 file2` and says program takes 4 args. 

Test:

```bash
./pipex
./pipex only_one_arg
./pipex a b c d e
echo $?
```

Expected:

* clean error message like `Usage: ./pipex file1 cmd1 cmd2 file2`
* exit with non-zero
* no leaks.

If your code segfaults while reading `argv[5]` that is an instant fail.

## 4. File descriptor discipline

Evaluator can run `lsof -p <pid>` or examine code.

You must prove:

* You close pipe ends in parent and in each child when not needed.
* You close infile fd and outfile fd after `dup2`.
* You wait for both children so no zombie.

You can rehearse like this:

### 4.1 Run a long blocking command

```bash
./pipex infile "cat" "cat" outfile &
pid=$!
sleep 1
lsof -p $pid
wait $pid
```

Check that only expected fds are open. No infinite hang.
If you forgot to close the write end of the pipe in the parent, `cat` in the second process may block forever waiting for EOF.

You should also know how your code avoids deadlock:

* child1 duplicates `infile` to STDIN and pipe[1] to STDOUT
* child2 duplicates pipe[0] to STDIN and `outfile` to STDOUT
* parent closes both pipe ends immediately after fork
* parent waits for both children.

Be able to draw this FD flow quickly.

## 5. Memory discipline

The subject is explicit. "All heap-allocated memory must be properly freed. Memory leaks will not be tolerated." 
"If your program quits unexpectedly (segfault etc.) the project is considered non-functional and you get 0." 

Evaluator will likely run something like:

```bash
valgrind --leak-check=full --show-leak-kinds=all ./pipex infile "grep o" "wc -l" outfile
```

You prepare for what they will look for:

Critical leak sources in pipex:

* Splitting cmd strings into `char **argv` arrays.
  Must free both in parent after forks or in children before `execve`?
  Note: after `execve` success you lose control, so you do not need to free in that path. But if `execve` fails you must free before exit.
* PATH resolution strings you `malloc`.
* Error paths. For example: file open fails then you return early. You must still free allocated command arrays, path strings, and close pipe fds that were opened so far.
* Protection against double free. Only free once.

You should rehearse:

* valid run
* invalid infile
* invalid command
  under valgrind.

If any "definitely lost" memory is reported at program exit you will get questions.

## 6. Signals and exit status

Less strict at pipex level but evaluators sometimes test `echo $?`.

They might run:

```bash
./pipex infile "grep nope" "wc -l" outfile
echo $?
< infile grep nope | wc -l > /tmp/shell_out
echo $?
```

They compare the final exit status of your program vs the last command in the pipeline.
In a normal shell pipeline, `$?` is the exit status of the last command in the pipeline. So they expect `pipex` to exit with `cmd2`'s exit status, not cmd1's.
You should set your main `exit(status_of_cmd2)` after `waitpid`.

If you always exit with 0 you can lose points.

## 7. Code understanding and live modification

The subject says you may be asked to modify code quickly to prove you understand your own work. 
You must be able to implement or explain on the spot:

High probability questions:

### 7.1 "Walk me through how data moves"

You should be able to whiteboard:

* `fork()` twice
* In first child:

  * `dup2(infile_fd, STDIN_FILENO)`
  * `dup2(pipefd[1], STDOUT_FILENO)`
  * `close(pipefd[0])`
  * `execve(cmd1_path, cmd1_args, envp)`
* In second child:

  * `dup2(pipefd[0], STDIN_FILENO)`
  * `dup2(outfile_fd, STDOUT_FILENO)`
  * `close(pipefd[1])`
  * `execve(cmd2_path, cmd2_args, envp)`
* Parent:

  * close both ends of pipe
  * `waitpid(child1)`
  * `waitpid(child2)`

If you cannot explain why each `dup2` is where it is, you will lose credibility fast.

### 7.2 "Add perror in this branch"

They may ask you to improve an error path. Example: "right now if `execve` fails you just exit(1). Update it so it prints the reason with `perror` first". You must be able to do that edit without breaking Norm and then recompile.

### 7.3 "Support absolute path check"

They may ask: "If cmd contains '/', skip PATH search and use it directly". You must show you know how your `get_cmd_path` works and patch it.

### 7.4 "Why no `system()`?"

You must answer: `system()` starts a full shell plus expansions and is not allowed. The assignment is specifically about reproducing the `< file1 cmd1 | cmd2 > file2` mechanism yourself using `fork`, `pipe`, and `execve`. 
So if you used `system`, you will fail outright.

### 7.5 Bonus questions even if they do not grade bonus

Be ready to explain how you would extend to:

```bash
./pipex file1 cmd1 cmd2 cmd3 ... cmdn file2
```

which must act like `< file1 cmd1 | cmd2 | ... | cmdn > file2`. 
Even if they cannot grade bonus unless mandatory is perfect, they may still ask orally. 
You should describe looped piping:

* N commands needs N-1 pipes
* Each middle child dup2(read_end_prev, STDIN) and dup2(write_end_next, STDOUT)

If you cannot outline this, they assume you copied code.
